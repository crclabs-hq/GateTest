## Quick start

```bash
# 1. Get an API key from gatetest.io/account (Phase 2: register an OAuth app)
export GATETEST_API_KEY=gt_live_xxxxxxxxxxxxxxxxxxxxxxxxxxxx

# 2. Verify the platform is reachable (no auth needed)
curl https://gatetest.io/api/v1/health
# → { "status": "ok", "version": "v1", "timestamp": "..." }

# 3. Start a scan
curl -X POST https://gatetest.io/api/v1/scans \
  -H "Authorization: Bearer $GATETEST_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "url": "https://customer-site.example",
    "suite": "web",
    "callbackUrl": "https://your-app.example/gatetest-webhook"
  }'
# → 201 Created
# → { "id": "scn_abc123", "status": "queued", ... }

# 4. Poll for results (or wait for the callback webhook)
curl https://gatetest.io/api/v1/scans/scn_abc123 \
  -H "Authorization: Bearer $GATETEST_API_KEY"
# → { "id": "scn_abc123", "status": "completed", "findings": [...] }
```

## Authentication

All endpoints (except `/api/v1/health`) require an API key.

Pass it in the `Authorization` header:

```
Authorization: Bearer gt_live_<32 alphanumeric>
```

OR (legacy alternative for clients that can't set Authorization):

```
X-API-Key: gt_live_<32 alphanumeric>
```

### Key prefixes

| Prefix | Mode | Anthropic spend |
|---|---|---|
| `gt_live_` | Production — real scans, real Claude calls, real billing | Real |
| `gt_test_` | Sandbox — returns canned results, free | None |

Develop your integration against `gt_test_` keys, switch to `gt_live_` for production. Same code, same endpoints, same response shapes — only the actual scan execution differs.

### Tiers

API keys are scoped to a tier that gates which suites they can run:

| Tier | Suites unlocked |
|---|---|
| `quick` | `web`, `quick`, `standard`, `wp` |
| `full` | All above + `full` (122-module deep scan) |
| `all` | Everything including `nuclear` (mutation, chaos, executive summary) |
| `admin` | All suites + bypass rate limits and per-scan billing |

Calling a suite outside your tier returns `403 TIER_INSUFFICIENT`.

### Admin-tier keys

The `admin` tier exists for **first-party / sibling-product integrations** — e.g. a sibling platform that consumes GateTest scans on behalf of its own customers and bills them separately, or owner-operated automation that needs unlimited internal use.

- Admin keys go through the **same code path** as every other key. The HMAC, the Bearer header, the request shape — identical to a regular customer.
- The only difference: `admin` keys bypass per-call rate limits and the Stripe billing pipeline.
- Admin keys are issued out-of-band by the platform owner. They are **not** purchasable through self-serve checkout. External integrators sit on `quick`, `full`, or `all` and pay normally.
- Any third party can become a paying integration partner with a regular tiered key — the public API is the same surface.

## Endpoints

### `GET /api/v1/health`

Liveness check. **Unauthenticated.** Use this for monitoring before exchanging tokens.

**Response (200):**
```json
{
  "status": "ok",
  "version": "v1",
  "timestamp": "2026-05-15T12:34:56.789Z"
}
```

The shape is **locked** — partners use this for liveness probes; we will never break it.

### `GET /api/health/deep`

Composite readiness. **Unauthenticated.** The liveness pings above (and `/api/health`, which the container HEALTHCHECK uses) return a constant body and cannot go red through a dead database, a silent scan queue or a rejected AI key. This endpoint can: point a monitor at it when you need a real verdict.

Five sub-checks, each with its own short timeout so the endpoint answers in about 2.5 s worst case and never hangs:

| Sub-check | Required | What it measures |
|---|---|---|
| `db` | yes | one round trip to the database |
| `queue` | yes | the scan queue is draining (dead-lettered jobs, jobs waiting past the ceiling, last worker activity) |
| `ai` | yes | the AI key is configured and the usage ledger recorded a successful AI call within 24 h — never a live paid call, so a quiet day reads `unknown`, not `ok` |
| `mail` | no | the configured mail provider answers a read-only question (nothing is sent) |
| `runtime` | no | the browser worker tier is configured and its status document reports healthy |

Per sub-check status: `ok` | `degraded` | `unknown` | `down` | `not-configured`. An optional sub-check that is not set up reports `not-configured` and does not affect the verdict.

**HTTP 503** when a required sub-check is `down` (or unconfigured); **200** otherwise. `status` is `ok`, `degraded` (something is unverified or an optional sub-check is failing) or `down`; `failing` names the sub-checks that are not `ok`.

**Response (200):**
```json
{
  "ok": true,
  "status": "ok",
  "failing": [],
  "checks": {
    "db":      { "status": "ok", "required": true,  "latencyMs": 14,  "reason": "connected" },
    "queue":   { "status": "ok", "required": true,  "latencyMs": 22,  "reason": "0 queued, 0 running, none stuck." },
    "ai":      { "status": "ok", "required": true,  "latencyMs": 9,   "reason": "last successful AI call 12 min ago" },
    "mail":    { "status": "ok", "required": false, "latencyMs": 310, "reason": "mail provider accepted the key" },
    "runtime": { "status": "not-configured", "required": false, "latencyMs": 0, "reason": "runtime worker not configured on this deployment" }
  },
  "checkedAt": "2026-09-28T23:59:00.000Z",
  "ttlSeconds": 30
}
```

The body carries sub-check names, statuses, latencies and templated reasons only — no configuration names, hostnames, providers or error text. The verdict is cached for 30 s (`Cache-Control: public, max-age=30`), so poll at that cadence or slower.

### `POST /api/v1/scans`

Start a new scan.

**Request body:**

| Field | Type | Required | Description |
|---|---|---|---|
| `url` | string | yes | The URL to scan. Must be public + http(s). Loopback / private IPs are rejected. |
| `suite` | string | no | One of `web`, `wp`, `quick`, `full`, `nuclear`. Default `web`. |
| `callbackUrl` | string | no | Where we POST the result when the scan completes. HMAC-signed. |
| `idempotencyKey` | string | no | If a duplicate is received within 24h, we return the original scan ID instead of creating a new one. |

**Response (201):**
```json
{
  "id": "scn_abc123def456",
  "status": "queued",
  "url": "https://customer-site.example",
  "suite": "web",
  "callbackUrl": "https://your-app.example/gatetest-webhook",
  "createdAt": "2026-05-15T12:34:56.789Z"
}
```

**Error responses:**

| Status | Code | Meaning |
|---|---|---|
| 400 | `BAD_REQUEST` | Invalid body (missing url, bad URL, invalid suite name) |
| 401 | `AUTH_FAILED` | Missing or invalid API key |
| 403 | `TIER_INSUFFICIENT` | Your key's tier doesn't include the requested suite |
| 429 | `RATE_LIMITED` | You've exceeded your per-hour rate limit |

### `GET /api/v1/scans/:id`

Read the status + (when complete) findings of a scan.

**Response (200) — queued or running:**
```json
{
  "id": "scn_abc123",
  "status": "queued",
  "url": "...",
  "suite": "web",
  "callbackUrl": "...",
  "createdAt": "..."

```

**Response (200) — completed:**
```json
{
  "id": "scn_abc123",
  "status": "completed",
  "url": "...",
  "suite": "web",
  "callbackUrl": "...",
  "createdAt": "...",
  "completedAt": "...",
  "healthScore": 73,
  "summary": {
    "errors": 5,
    "warnings": 12,
    "info": 3,
    "modulesRun": 18,
    "durationMs": 23847
  },
  "findings": [
    {
      "module": "wpExposedFiles",
```

**Error responses:**

| Status | Code | Meaning |
|---|---|---|

## Customer sign-in with email + password

Alongside GitHub / Google sign-in, a customer can create an account with an email address and a password (owner directive 2026-09-29). These routes are for the site's own pages, not for API clients — they set the same session cookie the OAuth callbacks set, and every POST must be same-origin (`Sec-Fetch-Site: same-origin`, or an `Origin` equal to the site origin; no header at all is refused with `403 csrf`). Bodies may be JSON or `application/x-www-form-urlencoded`; a form post is answered with a `303` back to the page (`?notice=` / `?error=` code), a JSON post with `{ ok, code }`.

| Route | Method | Inputs | Answers |
|---|---|---|---|
| `/api/auth/password/register` | POST | `email`, `password` (12+ chars, not on the common list), optional `password_confirm`, `next` | `200 verify_sent` (same for a known address), `400 email_invalid \| password_short \| password_long \| password_common \| password_mismatch`, `503 mail_unavailable` |
| `/api/auth/password/verify` | GET | `?token=` (and `next`) from the e-mail | `303 /login/password?notice=verified` — activates the password, sets no session (the click proves the mailbox, the password proves the person); `303 /login/password?error=token_invalid` |
| `/api/auth/password/login` | POST | `email`, `password`, `next` | `200 signed_in` + cookie; `401 bad_credentials` (one answer for unknown email / wrong password); `403 unverified` (right password, link re-sent); `429 throttled` |
| `/api/auth/password/forgot` | POST | `email` | `200 reset_sent` always; mail only when the address is known |
| `/api/auth/password/reset` | POST | `token`, `password`, optional `password_confirm` | `200 reset_ok`; `400 token_invalid \| password_*` |
| `/api/auth/password/change` | POST, signed in | `current_password`, `new_password`, optional `new_password_confirm` | `200 changed`; `400 current_wrong \| no_password \| password_*`; `401 not_signed_in` |

Pages: `/login/password`, `/login/password/register`, `/login/password/forgot`, `/login/password/reset?token=`, `/account/password` (behind the sign-in gate). Passwords are scrypt (`scrypt$N$r$p$salt$hash`, N = 2^15); a new password is not active until the emailed link is clicked, and issuing a new verify or reset link retires every outstanding one for that customer, so only the newest mail can activate a password; verify and reset links are single-use and valid for one hour; ten failed sign-ins per email + IP in 15 minutes are refused with `429` (counted in the database, so it holds across processes). No new environment variables: the routes need `SESSION_SECRET`, `DATABASE_URL` and the mail provider already configured for digests. Feature switch: `PASSWORD_AUTH_ENABLED` in `website/app/lib/auth-features.ts`.

## Webhooks (Phase 2 — coming next session)

When you supply `callbackUrl` on scan creation, we'll POST the result to that URL when the scan completes. Headers:

```
X-GateTest-Event:     scan.completed
X-GateTest-Delivery:  <uuid>
X-GateTest-Signature: sha256=<hmac-hex>
```

Verify the signature against the body using the secret you'll get when registering your app (Phase 2).

## Rate limits

| Tier | Requests / hour |
|---|---|
| Sandbox (test keys) | 100 |
| Standard | 1,000 |
| Partner | 10,000 |
| Enterprise | Negotiated |

Exceeded requests return `429 RATE_LIMITED` with a `Retry-After` header. Plan for backoff in your client.

## Status codes

| Code | Meaning | What to do |
|---|---|---|
| 200 | OK | Use the response body. |
| 201 | Created | Scan was queued successfully. |
| 400 | Bad Request | Check the `error` field — your body is malformed. |
| 401 | Unauthorized | Missing or wrong API key. |
| 403 | Forbidden | Key revoked OR tier insufficient. |
| 404 | Not Found | Scan ID doesn't exist or isn't yours. |
| 429 | Rate Limited | Slow down. Use exponential backoff. |
| 500 | Server Error | Our problem. Retry with backoff. |
| 503 | Service Unavailable | Briefly overloaded. Retry with backoff. |

## SDK (Phase 2)

```bash
npm install @gatetest/sdk
```

```js
import { GateTest } from '@gatetest/sdk';
const gt = new GateTest({ apiKey: process.env.GATETEST_API_KEY });
const scan = await gt.scans.create({ url: 'https://customer.example' });
const result = await gt.scans.poll(scan.id);
console.log(`Health score: ${result.healthScore}/100`);
```

Same code works in browser (with PKCE for OAuth in Phase 2), Node, edge runtimes.

## Versioning

- Endpoints live under `/api/v1/`. Breaking changes will land under `/api/v2/` — `/api/v1/` will stay supported for at least 12 months after a successor ships.
- Adding new fields to existing responses is NOT a breaking change. Your client should ignore unknown fields.
- Adding new endpoints is NOT a breaking change.
- Changing response shapes, removing fields, or changing auth requirements IS a breaking change — those go to `/api/v2/`.

## OAuth 2.0 (Phase 2 — preview)

The Phase 1 API uses API keys for simplicity. Phase 2 adds full OAuth 2.0 for partners building multi-user products.

```
1. Register your app:    https://gatetest.io/developers/apps/new
2. OAuth flow:           https://gatetest.io/oauth/authorize?...
3. Exchange code:        POST https://gatetest.io/api/v1/oauth/token
4. Use access_token:     same Bearer auth as API keys
```

See `docs/integration-platform-2026-plan.md` for the full architecture.
